# 0010. Signed assistant turns for the chat's history

- Status: Accepted
- Date: 2026-11-24
- Extends: [0005](0005-security-baseline.md)

## Context

The "Ask about me" chat sends the whole conversation to Claude on every request, because the API is stateless. Nothing
stores the conversation: there is no table, no session and no tracking cookie, which the privacy rules require. So the
history has to come back from the browser with each request.

The browser is not trusted. A visitor can edit an earlier answer ("Mirel was CTO for five years") and the model would
repeat it as if it had said it. Answers must be grounded in tool results, so the server has to know which assistant
turns it really produced.

## Decision

- **The browser holds the history.** Each request carries the conversation.
- **The server signs every assistant turn it sends.** The signature is HMAC-SHA256 over the role, the conversation id,
  the position, the content, the issue time and the expiry time, with a key of at least 256 bits from the environment.
  The key is validated with zod and never sent to the client. The signature is 64 lowercase hex characters.
- **The server verifies every assistant turn it receives and keeps only the valid ones.** A turn is valid when its
  signature checks out, its conversation id is the current conversation's, its position is its place in the request,
  and it has not expired (15 minutes after issue). Invalid turns are dropped, not repaired.
- **The conversation id is a UUID generated by the server with the first answer.** It is signed with every turn, so a
  turn cannot be moved to another conversation.
- **The signing code is pure.** It lives in `apps/web/src/server/chat-turn-signature.ts`. The key, the clock and the
  time to live are parameters, so the functions are tested without the environment.
- **The visitor's own messages are not signed.** They are input: zod validates them against the limits of
  `@mirelnan/ai` (see the chat input limits).
- **Only the verified fields reach the model.** The route passes `role` and `content` of each valid turn to
  `chatConversationSchema`, which is strict and does not know the signed fields.

## Alternatives considered

- **Send only the visitor's messages to the model.** Simplest, and nothing forged reaches the model. But follow-up
  questions lose their context ("and since when?" has no referent).
- **Store the conversation on the server, under a session id.** The server becomes the source of truth and can revoke a
  conversation or limit it. It costs a table, a retention policy and personal data to protect, and it breaks the
  no-tracking rule without an explicit decision. Rejected for a portfolio. Revisit only with a new ADR.
- **Sign the whole conversation as one unit.** It binds the turns to each other more strongly, but every change re-signs
  everything, and a streamed answer cannot be signed before it is complete. Rejected in favour of one signature per turn.

## Consequences

- (+) No conversation is stored: no table, no retention policy, no personal data.
- (+) A visitor cannot inject an answer the server did not produce, and cannot move an answer into another conversation.
- (+) Verification is stateless and runs on any instance of the serverless function.
- (+) Forged or expired turns are removed, so the model always sees a history the server could have produced.
- (−) The key is a new secret. It must be generated, stored as a Sensitive variable on Vercel and rotated. Rotating it
  invalidates the conversations in progress, which is acceptable for a 15-minute window.
- (−) A visitor can still delete turns from their own history. The server can prove each turn is genuine, not that the
  history is complete.
- (−) The server cannot revoke a conversation before it expires, and cannot limit usage per conversation without
  storage. Rate limiting stays per IP ([9a](../../CLAUDE.md)).
- (−) A genuine answer can be replayed in the same conversation within its 15 minutes; the expiry bounds this.
- (−) Each assistant turn adds about 200 bytes to every request (signature, ids and times). That is small next to the
  text.

## Notes for the implementation

- The verification order is: shape, signature, conversation, position, expiry. The signature is checked first, so a
  tampered field is always reported as tampered.
- The signature is compared with `timingSafeEqual`, after a length check, because it throws on different lengths.
- Revisit this ADR if per-conversation limits or revocation become necessary: they need a server-side store, which
  means a new ADR that supersedes this one.
